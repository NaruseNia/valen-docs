# Classes

## Class Declaration

```valen
class User(pub name: String, mut age: Int) {
    fn greet(self) -> String {
        f"Hello, {self.name}!"
    }

    // associated function — no self receiver, called via User::...
    fn from_name(name: String) -> User {
        User(name = name, age = 0)
    }
}
```

Classes are **final by default**. Methods can be defined directly in the class body or added later via inherent `impl` blocks. Trait implementations are always separate: `impl Trait for Class { ... }`.

## Primary Constructor Parameters

Every class has a mandatory primary constructor. Parameters declare the class fields.

| Modifier    | Visibility  | Mutability | Example              |
|-------------|-------------|------------|----------------------|
| *(none)*    | Internal    | Immutable  | `name: String`       |
| `pub`       | Public      | Immutable  | `pub name: String`   |
| `pub mut`   | Public      | Mutable    | `pub mut age: Int`   |
| `private`   | Private     | Immutable  | `private name: String` |
| `mut`       | Internal    | Mutable    | `mut age: Int`       |

- **Unmodified** parameters are `internal` — visible within the same package, invisible outside.
- `pub` / `internal` / `private` can be specified per-parameter.
- Modifier order: visibility first, then `mut` — `pub mut`, not `mut pub`.

Constructor parameters support default values:

```valen
class Config(pub host: String = "localhost", pub port: Int = 8080) {}
```

## Inherent `impl` Blocks

Methods can be added to a class outside its body using `impl Type { ... }`:

```valen
// Methods in the class body
class Foo(pub x: Int) {
    fn bar(self) -> Int { self.x }
}

// Methods via inherent impl
impl Foo {
    fn baz(self) -> Int { self.x * 2 }
}
```

- Inherent impl methods have the same resolution priority as class body methods.
- `fn method(self)` — instance method, called as `foo.bar()`.
- `fn assoc(x: T)` (no `self`) — associated function, called as `Foo::assoc(x)`.
- Trait implementations are always separate: `impl Trait for Foo { ... }`.

## `derives(...)` Clause

Classes and data classes can declare `derives(...)` to auto-generate standard methods.

```valen
class Foo(pub x: Int, pub y: Int) derives(Eq, Hash) {
    fn bar(self) -> Int { self.x + self.y }
}

data class Point(x: Float, y: Float) derives(Eq, Hash, Display, Clone);
```

**Syntax:** `derives(Trait1, Trait2, ...)` — placed after constructor parameters (and supertype clause, if any), before the body `{` or terminating `;`.

### Derivable Traits

| Trait     | Generated Method                | Behavior                          |
|-----------|---------------------------------|-----------------------------------|
| `Eq`     | `equals(Object) -> Boolean`     | Field-by-field structural comparison |
| `Hash`   | `hashCode() -> Int`             | 31-multiply-accumulate algorithm  |
| `Display` | `toString() -> String`         | `ClassName(field=value, ...)` format |
| `Clone`  | `copy(...) -> Self`             | All-field copy constructor        |

`data class` automatically derives all four — explicit `derives(...)` is redundant but harmless. Use `derives(...)` on plain `class` or `enum` to opt in.

## `data class`

```valen
data class Point(x: Float, y: Float);
data class User(pub name: String, pub email: String);
```

### Auto-generated Methods

| Method       | Behavior                                |
|--------------|-----------------------------------------|
| `equals`     | Field-by-field structural comparison    |
| `hashCode`   | 31-multiply-accumulate over all fields  |
| `toString`   | `TypeName(field=value, ...)` format     |
| `copy`       | Copy constructor with named overrides   |

Auto-generation considers **only the primary constructor parameters** of the data class itself (not inherited state).

### Restrictions

| Rule                       | Detail                                           |
|----------------------------|--------------------------------------------------|
| Always `final`             | Cannot be subclassed                             |
| No `open` / `abstract` / `sealed` | These modifiers are forbidden on data class |
| Cannot be a superclass     | Other classes cannot extend a data class         |
| Can extend sealed/open/abstract class | Usable as a leaf in sealed hierarchies |
| Trait impl allowed         | `impl Trait for DataClass { ... }` works         |
| Inherent impl allowed      | `impl DataClass { ... }` works                  |
| Semicolon terminator       | Body-less data class ends with `;`               |

::: warning Known Limitation
Supertype syntax (`: SuperClass(args)`) is parsed, but the supertype information is **lost during HIR lowering**. Data classes currently always extend `java.lang.Object` in the generated bytecode. This will be fixed in a future release.
:::

## `open` / `abstract` / `sealed` class

| Modifier   | Subclassable | Can instantiate | Methods                     |
|------------|-------------|------------------|-----------------------------|
| *(none)*   | No (final)  | Yes              | All concrete                |
| `open`     | Yes         | Yes              | Mark overridable methods with `open fn` |
| `abstract` | Yes         | No               | May have `abstract fn` (no body)        |
| `sealed`   | Yes (same module only) | No      | Closed hierarchy for exhaustive match   |

```valen
open class Animal(pub name: String) {
    open fn speak(self) -> String { "..." }
}

abstract class Shape {
    abstract fn area(self) -> Float;
}

sealed class Payment;
class Card(pub number: String) : Payment();
data class Cash : Payment();
```

`open` does not cascade — if `B : A` and `B` itself should be subclassable, `B` must also be declared `open`.

Abstract methods use `;` termination and must not have a body. Providing a body on an `abstract fn` produces a compile error (`ABSTRACT_METHOD_HAS_BODY`). Non-abstract methods without a body also produce an error (`NON_ABSTRACT_MISSING_BODY`).

## `sealed class` / `sealed trait` Bytecode

| Valen | JVM Bytecode |
|-------|--------------|
| `sealed class Foo` | `abstract class Foo` + `PermittedSubclasses` attribute |
| `sealed trait Foo` | `interface Foo` (abstract + interface) + `PermittedSubclasses` attribute |

Sealed classes/traits leverage JVM sealed classes (JEP 360/397, JDK 17+). The `PermittedSubclasses` class file attribute enumerates the permitted subtypes.

## `override fn`

Overriding a parent method requires both `open fn` on the parent and `override fn` on the child.

```valen
class Dog(pub name: String) : Animal(name) {
    override fn speak(self) -> String { "woof" }
}
```

- Omitting `override` when shadowing a parent method is a compile error.
- `override` is only required when the signature matches a parent `open fn`.
- If signatures differ (by arity or type), the same name can coexist without `override`.
- Class body methods do **not** satisfy trait requirements — trait implementations must be in `impl Trait for Type { ... }` blocks.

## Superclass Constructor Call

The superclass constructor is called in the inheritance clause:

```valen
class Dog(pub name: String) : Animal(name) {
    // ...
}
```

Arguments are passed directly to the parent's primary constructor.

## `super` Calls

`super.method()` calls the parent **class** method only. To call a trait default method, use UFCS: `Trait::method(self)`. Since Valen uses single class inheritance, `super` is never ambiguous.

## Class Body Restrictions

The class body only supports **method declarations**. Field declarations inside the class body are not supported by the current parser — fields are defined exclusively as constructor parameters. Encountering a non-method token in the class body produces a parse error.

## Method Resolution Order

When resolving `value.foo(args)`, the compiler follows this order:

1. **Class body** — methods defined inside the class declaration (highest priority).
2. **Inherent impl** — methods from `impl Type { ... }` blocks.
3. **Trait methods** — in-scope trait methods (lowest priority).
4. **Ambiguity error** — if multiple trait candidates match and cannot be distinguished.

Disambiguate with UFCS: `Trait::foo(value, args...)`.

`Class::foo(args...)` is only for associated functions (no `self`). Instance methods always use dot syntax.

## Associated Functions vs Top-level Functions

`parse(x)` resolves as a top-level function. `User::parse(x)` resolves as an associated function on `User`. The two namespaces do not merge.

**Recommendations:**
- **Associated function** — factory methods, constructors, anything that touches type internals (`from_*`, `parse`, `zero`, `default`)
- **Top-level function** — algorithms over multiple types, stateless utilities, pure functions

## Unsupported Features

- `init { ... }` blocks
- Secondary constructors
- Field overrides (`override val`)
- Nested / inner classes
- Field declarations in class body (constructor parameters only)
- Abstract method bodyless declaration (parser requires body)
- Data class supertype codegen (supertype info lost in HIR lowering)
